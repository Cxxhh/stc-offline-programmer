# STC单片机离线烧录器 产品需求文档 (PRD)

**版本**: 1.0.0  
**创建日期**: 2025-12-10  
**项目代号**: STC-ISP-Programmer  
**目标平台**: STM32G4xx (STM32G431RBTx)

---

## 1. 目标与背景

### 1.1 目标

- 开发一款基于STM32G4xx平台的STC单片机离线烧录器，实现无PC独立烧录功能
- 支持STC 89/10/11/12/15/8全系列单片机（1140+型号），覆盖市场主流STC芯片
- 实现自动识别目标MCU型号，降低用户操作门槛
- 提供友好的LCD显示界面与按键交互，提升用户体验
- 支持SD卡固件存储，实现多固件管理与批量烧录
- 建立可扩展的软件架构，为后续功能迭代奠定基础

### 1.2 背景

STC系列单片机因其高性价比和易用性在国内嵌入式领域广泛应用。然而，STC官方仅提供Windows平台的GUI烧录工具，且依赖PC进行在线烧录，在生产线批量烧录、现场维护、无PC环境等场景下存在明显局限性。

当前市场上缺乏功能完善的STC离线烧录方案。开源项目如stcgal（Python）和stc8prog提供了协议逆向成果，但均为PC端工具。本项目旨在填补这一空白，基于STM32G4xx强大的处理能力和丰富的外设资源，开发一款便携式离线烧录器，为STC单片机开发者和生产厂商提供高效、便捷的烧录解决方案。

## 2. 需求

### 2.1 功能需求

**核心功能（P0 - 必须实现）**

- **FR1**: 系统应支持通过UART与STC目标单片机通信，实现ISP握手协议
- **FR2**: 系统应能通过Magic码自动识别目标STC单片机型号（支持1140+型号数据库）
- **FR3**: 系统应支持将用户代码烧录到STC单片机的Code Flash区域
- **FR4**: 系统应支持对STC单片机进行全片擦除操作
- **FR5**: 系统应在烧录完成后进行数据完整性校验，确保烧录正确
- **FR6**: 系统应支持STC89/10/11系列（8N1模式）和STC12/15/8系列（8E1偶校验模式）的串口配置切换
- **FR7**: 系统应支持动态波特率切换，握手阶段使用低速（2400bps），数据传输阶段协商高速（最高230400bps）

**扩展功能（P1 - 应该实现）**

- **FR8**: 系统应支持将数据烧录到STC单片机的IAP/EEPROM区域
- **FR9**: 系统应通过LCD显示目标MCU的型号、Flash大小、UID等设备信息
- **FR10**: 系统应支持从SD卡读取HEX/BIN固件文件进行烧录
- **FR11**: 系统应支持在SD卡上存储和管理多个固件文件
- **FR12**: 系统应提供按键操作界面，支持固件选择、烧录启动、状态查看等基本操作

**高级功能（P2 - 可以实现）**

- **FR13**: 系统应支持STC15/8系列的内部RC振荡器频率校准功能
- **FR14**: 系统应支持配置目标MCU的熔丝位/选项字节
- **FR15**: 系统应支持测量目标MCU的实际工作频率

**未来功能（P3 - 后续版本）**

- **FR16**: 系统应支持批量烧录模式，实现连续自动烧录
- **FR17**: 系统应支持STC32系列（MCS-251架构）单片机的烧录

### 2.2 非功能需求

**性能需求**

- **NFR1**: 握手响应时间应小于3秒（包含目标MCU冷启动时间）
- **NFR2**: 单次烧录64KB代码的时间应小于30秒（不含擦除时间）
- **NFR3**: 系统应支持连续工作8小时以上无异常

**可靠性需求**

- **NFR4**: 烧录成功率应达到99.9%以上
- **NFR5**: 系统应具备通信超时检测和错误重试机制
- **NFR6**: 系统应在烧录失败时提供明确的错误提示

**可维护性需求**

- **NFR7**: 代码应遵循嵌入式分层架构规范（Port/BSP/Middlewares/Service/APP）
- **NFR8**: 模块间应通过统一设备接口通信，采用依赖注入保持低耦合高内聚
- **NFR9**: MCU数据库应支持独立更新，无需重新编译整体固件

**资源约束**

- **NFR10**: 固件大小应控制在128KB Flash以内（STM32G431RBTx限制）
- **NFR11**: 运行时RAM占用应控制在32KB以内（STM32G431RBTx限制）
- **NFR12**: 应优先使用LL库而非HAL库，以优化代码体积和执行效率

## 3. 用户界面设计目标

### 3.1 整体UX愿景

提供简洁直观的嵌入式设备界面，以最少的操作步骤完成烧录任务。界面风格应体现专业工具属性，信息展示清晰，操作反馈及时。

### 3.2 关键交互范式

- **状态导向**：主界面始终显示当前设备状态（空闲/检测中/烧录中/完成/错误）
- **即时反馈**：每个操作步骤提供实时进度和结果反馈
- **容错设计**：关键操作需确认，误操作可恢复
- **最小化输入**：利用自动检测减少手动配置

### 3.3 核心屏幕与视图

| 屏幕 | 功能 | 优先级 |
|------|------|--------|
| 主状态屏 | 显示烧录器状态、目标MCU信息、当前固件 | P0 |
| 固件列表屏 | 浏览SD卡固件文件，选择待烧录固件 | P1 |
| 烧录进度屏 | 显示烧录进度条、当前步骤、耗时 | P0 |
| 设备信息屏 | 详细显示目标MCU型号、Flash/EEPROM大小、UID | P1 |
| 设置屏 | 系统配置（波特率、超时时间等） | P2 |
| 错误详情屏 | 显示错误码、错误描述、建议操作 | P0 |

### 3.4 可访问性

- 基础可访问性：高对比度显示，适合工业环境光照条件
- 不强制要求WCAG标准（嵌入式设备限制）

### 3.5 品牌与风格

- 工业风格：深色背景 + 高亮状态色
- 状态色定义：
  - 成功/正常：绿色
  - 进行中：蓝色
  - 警告：黄色
  - 错误：红色
- 字体：清晰的等宽字体，适合显示HEX数据和技术参数

### 3.6 目标设备与平台

- 主显示：复用现有工程 LCD 驱动（`Src/lcd.c` + `Inc/lcd.h`），驱动已完成调试，可直接调用，本项目不重新开发 LCD 驱动层，仅负责基于该驱动实现显示逻辑，并确保 LCD 显示内容与串口调试输出保持一致
- 输入：物理按键（4-6键）
- 不涉及Web/Mobile平台

## 4. 技术假设

### 4.1 仓库结构

**结构类型**: Monorepo

本项目采用单一仓库结构，所有代码（HAL/BSP/Service/APP）在同一仓库内管理，便于版本控制和依赖管理。

### 4.2 服务架构

**架构类型**: 分层单体架构（含Port层抽象）

```
┌─────────────────────────────────────────────────────────────────────────┐
│                              APP Layer                                   │
│                    (app_main, app_ui, app_isp)                          │
│                      业务逻辑 / UI交互 / 流程控制                          │
├─────────────────────────────────────────────────────────────────────────┤
│                           Service Layer                                  │
│              ┌─────────────┬─────────────┬─────────────┐                │
│              │  ISP Core   │  File Mgr   │   Config    │                │
│              │  烧录状态机  │  固件管理   │   配置管理   │                │
│              └─────────────┴─────────────┴─────────────┘                │
├─────────────────────────────────────────────────────────────────────────┤
│                         Middlewares Layer                                │
│       ┌──────────┬──────────┬──────────┬──────────┬──────────┐         │
│       │  FatFs   │   Log    │ RingBuf  │ Protocol │  MCU DB  │         │
│       │ 文件系统  │  日志    │ 环形缓冲  │ ISP协议  │ 型号数据  │         │
│       └──────────┴──────────┴──────────┴──────────┴──────────┘         │
├─────────────────────────────────────────────────────────────────────────┤
│                         Device Layer (BSP)                               │
│       ┌─────────────────────────────────────────────────────────┐       │
│       │              Unified Device Interface                    │       │
│       │                 统一设备接口抽象                          │       │
│       ├─────────────────────────────────────────────────────────┤       │
│       │   Serial Dev   │   Display Dev   │   Storage Dev        │       │
│       │   串口设备      │    显示设备      │    存储设备          │       │
│       └─────────────────────────────────────────────────────────┘       │
├─────────────────────────────────────────────────────────────────────────┤
│                      Platform Port Layer (HAL)                           │
│       ┌───────────────┬───────────────┬─────────────────────────┐       │
│       │  STM32G4 Port │  STM32F1 Port │   Other MCU Port        │       │
│       │   (LL库实现)   │   (LL库实现)  │     (待扩展)            │       │
│       └───────────────┴───────────────┴─────────────────────────┘       │
└─────────────────────────────────────────────────────────────────────────┘
```

**设计原则**:
- 单向依赖：只允许上层调用下层
- 接口隔离：每层通过统一接口对外暴露功能
- 依赖注入：上层模块不直接依赖具体实现，运行时注册设备实例
- 可替换性：更换平台只需重写Port层，BSP层设备实现可独立替换

### 4.3 测试需求

**测试策略**: Unit + Integration

- **单元测试**: 协议解析、数据校验、状态机逻辑
- **集成测试**: 串口通信、SD卡读写、完整烧录流程
- **手动测试**: 实际STC芯片烧录验证

### 4.4 其他技术假设与要求

**硬件平台**
- MCU: STM32G431RBTx (ARM Cortex-M4, 80MHz, 128KB Flash, 32KB SRAM)
- 开发环境: Keil MDK-ARM
- 底层库: STM32 LL库（非HAL库）

**通信配置**
- 目标通信: USART2 (PA2/PA3)，支持动态波特率和校验位切换
- 调试输出: USART1 (115200, 8N1)
- SD卡通信: SPI1

**外部依赖**
- FatFs: 文件系统中间件（SD卡固件存储）
- MCU数据库: 源自stcgal开源项目（1140型号）

**编码规范**
- 遵循嵌入式5层架构规范
- 函数命名: `hal_xxx()`, `bsp_xxx()`, `svc_xxx()`, `app_xxx()`
- 返回值约定: 0=成功, 负数=错误码
